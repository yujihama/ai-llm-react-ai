## モデル選択例の実行方法と限界

`model_selected/C_deferred`と`model_selected/C_unavailable`は、それぞれ新規コンテキストの単一LLMエージェントによる1回の実行です。初期入力はそれぞれ中立名`trial_a`、`trial_b`で提示され、初期入力の本文は2条件でバイト単位に一致します。試行内では同じ会話を継続し、初回は初期入力、その後は最新観測を渡しました。全履歴入力を毎回重複して送ってはいません。

実行担当者の記録によると、評価を行うLLMは講師用資料・正解表にアクセスせず、提示された入力と観測だけを利用しました。ラッパー指示は参照元を制限し、行動JSONを1個だけ返すよう求めるものです。実行担当者は選ばれた行動JSONを修正せずに中継しました。`trial_a`の最初の観測だけはJSONの空白を詰めて貼り付け、その後の継続用観測と`trial_b`の継続用観測はUTF-8ファイルを評価を行うLLMだけに読取許可して渡しました。

正確なモデル版、temperature、応答時間、トークン数、料金は記録されていません。各条件1回の例であり、成功率、モデル間の優劣、他の業務への改善率や一般化を示すものではありません。

`scripted`以下は講師作成の行動列のローカル再生です。LLMが行動を選んだ実測として扱いません。

## ファイルの読み方

各条件の`provenance.json`に出典・中継方法・コードのハッシュ・測定上の限界を記載しています。

- `initial_prompt.txt`：固定指示・手続・初期証跡から再構成した初回入力。
- `model-action-XX.json`または`action-XX.json`：元の行動JSONをバイト単位で保持したもの。
- `trace.jsonl`：元の全行動・観測履歴を保持したもの。
- `step-XX-observation.txt`：その時点の最新観測、残り手数、状態。保存済み履歴と同じランタイムから再構成しています。
- `final_prompt.txt`：元の最終全履歴入力。再構成結果との完全一致を検証しています。
- `latest_observation.txt`：元の最後の観測ファイル。
- `final_result.json`：受理された4条件の提出結果。
- `step_metrics.json`：各手の前後に再構成した全履歴入力の文字数とハッシュ、行動・観測の文字数。

step観測ファイルは通信の生ログではありません。特に`trial_a`の最初の中継は空白を詰めており、正確な送信文字数は未記録です。`state.json`や未観測資料を含む内部一覧は収録していません。

## ローカル制御の検証

[runtime_verification.json](runtime_verification.json)に、31項目・38回の起動による検証結果とコードのSHA-256を収録しています。完全行の可視性、手数上限・重複・終了制御、数値と日時の比較、入力・状態・保存の整合性を確認しています。これはランタイムの検証であり、LLMの回答品質の検証ではありません。

集計値は[metrics_summary.json](metrics_summary.json)にあります。
